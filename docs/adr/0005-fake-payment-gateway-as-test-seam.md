# 0005. Поддельный шлюз платежей как шов для тестов

## Контекст

Сквозной путь покупки (корзина, оформление, вебхук, возврат, остаток мест) нужно проверять тестами, которые идут без сети и ключей Stripe. Настоящий Stripe проверяется вручную один раз.

## Решение

Платёж скрыт за интерфейсом `PaymentGateway` (`createCheckout`, `retrieveSession`, `constructEvent`, `ensureTaxRate`, `ensureProduct`) и функцией `gateway()`. Реализаций две: Stripe через официальный SDK и поддельная, живущая в памяти процесса. Поддельная включается переменной `PAYMENT_GATEWAY=fake` и отдаёт страницу `/checkout/fake`, где тест «платит» или «бросает» оплату. Поддельный шлюз — часть HTTP-шва тестов сайта, а не отдельный третий шов.

## Почему

- Тесты против тестового режима Stripe. Отвергнуто: нужны сеть и секретные ключи при каждом прогоне, тесты медленнее и зависят от внешнего сервиса, а ключи нельзя хранить в репозитории.
- Подмена SDK в каждом тесте. Отвергнуто: тесты проверяли бы собственные моки, а не маршруты сайта; шов на уровне интерфейса оставляет настоящие маршруты (`POST /checkout`, `/checkout/fake`, `POST /stripe/webhook`).
- Вебхук в тестах подписывается так же, как настоящий, через `generateTestHeaderString`, поэтому проверка подписи не обходится.

## Последствия

- Поддельный шлюз может разойтись с поведением настоящего: единственная проверка реальности — ручная покупка тестовой картой через Stripe CLI (`listen`) и на staging.
- Интерфейс из пяти методов приходится держать узким и обновлять в обеих реализациях.
- Состояние поддельного шлюза хранится в памяти процесса и теряется при рестарте сервера.
- `PAYMENT_GATEWAY=fake` не должна попасть в окружение продакшена: тогда оплата станет бутафорской. Маршрут `/checkout/fake` существует только при этой переменной.
